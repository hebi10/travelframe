# 보안 점검 — 2026-09-20

## 보완 작업 결과

아래 본문은 수정 전 감사 결과다. 이후 사용자 승인으로 계정 소유 보관함 잠금·구독 응답 경합 방지·신규 백업 인증 다운로드·구매 검증 제한 및 의존성 패치를 로컬 코드에 반영했다. 기존 기록/기존 다운로드 토큰/Drive 공유/운영 배포는 변경하지 않았다.

검증: 전체 기본 테스트 263개 파일, 별도 Firebase Rules 에뮬레이터, TypeScript, ESLint, Functions 구문 검사, 현재 작업 트리 비밀값 검사 통과. 새 인증 다운로드와 계정 잠금의 Android 실기기 QA 및 운영 배포는 아직 수행하지 않았다. npm audit 앱 critical/high 0·moderate 3, Functions 0.

배포 순서·기존 링크 폐기·App Check 강제 적용의 남은 작업은 [운영 반영 문서](security-hardening-rollout.md)를 따른다. 새 private 업로드는 구버전 앱에서 열리지 않을 수 있어 앱 업데이트를 함께 검증해야 한다.

## 결론과 범위

일반 사용자가 다른 UID의 백업을 읽거나 서버 구독을 직접 수정하는 허용 경로는 이번 검토에서 발견하지 못했다. 그러나 아래 보완 사항이 있어 전체 서비스가 안전하다고 단정할 수 없다. 침해 이력 조사나 침투 테스트를 수행한 것은 아니다.

코드, 로컬 Firestore/Storage 규칙, 관리자 화면 코드, 결제 검증 로직, Google Drive 프로젝트 폴더 공유 메타데이터, 운영 Firebase 콘솔의 주요 규칙을 읽기 전용으로 확인했다. 제품 코드·공유 권한·운영 규칙·출시는 변경하지 않았다.

## 우선 보완 사항

### 1. 다운로드 링크 유출 시 사진·영상 접근 가능 — P2

- 근거: `lib/cloud-backup.ts:416` getDownloadURL; `:1331` 이후 사진 URI/미리보기/다운로드 링크 저장. `functions/index.js:657`에서도 토큰 URL 생성.
- Firebase 다운로드 토큰 URL은 공유 가능한 장기 링크다. 소유 UID가 아니면 Storage SDK 읽기는 거절되지만, 이 링크 자체가 유출되면 비로그인 다운로드가 가능하다. 파일이 검색엔진이나 모든 사용자에게 공개돼 있다는 뜻은 아니다. 이번 점검에서 실제 유출은 발견하지 않았다.
- 백업 메타데이터를 읽는 관리자도 링크로 사진을 볼 수 있는 구조다. 종단간 암호화 구조가 아니다.
- 권고: 민감 사진은 사용자 인증을 확인하는 다운로드와 로컬 캐시로 전환. 기존 토큰 폐기는 기존 복원·미리보기·영상 기능에 대한 마이그레이션과 함께 진행.
- 공식 근거: https://firebase.google.com/docs/reference/kotlin/com/google/firebase/storage/StorageReference

### 2. 같은 기기의 계정 전환 시 로컬 사진·프로젝트 혼합 — P2

- 근거: `lib/auth-context.tsx:163` 로그아웃은 signOut만 수행. `lib/legacy-photo-library.ts:18`, `lib/body-project-library.ts:6` 저장키에 UID가 없다.
- `lib/cloud-backup.ts:785` 전체 백업은 공통 로컬 사진을 읽어 현재 계정에 업로드한다. `:1834` 복원은 로컬 사진과 현재 계정의 백업을 합친다.
- 시나리오: A의 사진이 남은 폰에서 B로 로그인하면 사진이 계속 보이며, B가 유료 백업 조건을 충족해 전체 백업할 경우 B 클라우드에도 복제될 수 있다. 원격에서 다른 UID를 침범하는 문제와는 다르다.
- 권고: UID별 라이브러리/캐시 분리, 게스트 자료 가져오기는 명시적 선택, 계정 전환 시 진행 중인 백업 취소 또는 소유자 고정. 자료를 무조건 삭제하는 방식은 피한다.

### 3. 늦게 도착한 구독 조회가 다른 계정의 로컬 권한에 적용될 가능성 — P2

- 근거: `lib/auth-context.tsx:119–140`, `:181–187`에서 비동기 조회 완료 후 현재 UID/요청 세대를 검증하지 않는다. `:197`의 유료 권한 판정은 해당 상태를 사용한다.
- 유료 A의 조회 도중 무료 B로 바꾼 뒤 A 응답이 늦게 완료되면 B에게 A의 로컬 유료 기능이 일시 적용될 수 있다. 정적 제어 흐름으로 확인했으며 실제 기기에서 재현하지 않았다.
- 서버 구독 변경이나 다른 사용자 Storage 접근까지 허용된다는 증거는 없다.
- 권고: 인증 요청 세대와 현재 UID 일치 시에만 상태 반영, 전환 즉시 구독 상태 초기화, refreshUser도 동일 보호.

### 4. 결제 검증 API 반복 호출 비용·쿼터 방어 부족 — P2

- 근거: `functions/index.js:73`, `functions/google-play-billing.js:204`, `:235`, `:397`.
- 정상 로그인 사용자가 같은 구매 토큰을 반복 검증하면 매번 Google API 조회와 신규 paymentEvents 쓰기가 발생한다. 실제 서비스 코드를 mock 환경에서 3회 호출하여 외부 조회 3회/이벤트 3개를 재현했다. 실제 결제 서비스에 반복 요청하지 않았다.
- App Check 강제는 `functions/index.js:37` 환경변수에 의존하며 클라이언트 초기화 구현은 발견하지 못했다. 운영 환경변수와 App Check 강제 여부는 미확인이다.
- 권고: UID별 호출 제한, 짧은 중복 검증 캐시, 이벤트 멱등성, Android App Check 도입. App Check만으로 정상 계정의 남용까지 해결되지는 않는다.

### 5. 운영 배포 일치 여부와 의존성 보완

- 운영 Firestore 콘솔의 활성 규칙은 2026-06-10 배포본이다. 구독/관리자 쓰기 금지와 소유자·관리자 메타데이터 읽기 제한은 직접 확인했다. 하지만 최신 로컬 규칙과 일부 본문이 달라 전체 동기화 상태는 보장할 수 없다.
- 운영 Storage에서도 소유자 read, 예약된 create, 임의 update/delete 금지, 나머지 경로 기본 거부를 확인했다. 전체 규칙의 바이트 단위 비교 및 배포된 Cloud Functions 소스/환경변수 검증은 수행하지 못했다.
- `npm audit --omit=dev`: 앱 의존성 19건(critical 1, high 12, moderate 6), Functions 5건(high 1, moderate 4). 이는 패키지 경고 수이며 실제 공격 가능성이 확인된 취약점 수가 아니다.
- critical 경고의 websocket-driver는 Firebase Realtime Database 의존성 경로다. 프로젝트에서 firebase/database 직접 사용은 발견하지 못했다. Metro 등 빌드 도구도 앱 의존성 트리에 포함되어 있어 Android 출시 앱에 그대로 노출된다고 판단하면 안 된다.
- 권고: 호환 가능한 보안 패치 업데이트 후 빌드/로그인/결제/백업 검증. 무조건적인 `npm audit fix --force`는 피한다.

## Google Drive

이전에 공유된 `02_바디프레임앱` 폴더의 실제 권한은 owner만 있으며 shared=false였다. 접근 가능한 하위 폴더와 문서를 재귀적으로 메타데이터 조회한 범위에서도 shared=true 항목을 발견하지 못했다. 공개 링크/도메인/다른 사용자 권한은 상위 폴더에 없었다. 폴더 외부 파일이나 다른 계정의 Drive는 범위 밖이다.

앱의 사진 클라우드 백업은 Google Drive API가 아니라 Firebase Storage를 사용한다. 위 Drive 결과와 Firebase 사진 링크 위험은 별개다.
