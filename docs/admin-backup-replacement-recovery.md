# 관리자 백업 슬롯 교체: 진행 상태 및 재시도

관리자 슬롯 교체는 현재 기본 비활성입니다. FUNCTIONS_ENABLE_ADMIN_BACKUP_DELETION 설정을 true로 변경하지 않습니다.

- 교체 시작 전 다른 관리자 작업/기존 프로젝트에 예약된 업로드를 확인하고 거부합니다.
- 서버 트랜잭션에서 슬롯을 replacing으로 표시하고 새 projectId를 pendingProjectId에 기록합니다.
- 해당 슬롯의 신규 업로드를 차단합니다. 이후 기존 프로젝트의 Storage/Firestore 데이터를 삭제하고, 새 프로젝트 슬롯으로 전환합니다.
- 중간 삭제 실패 시 replacing 상태가 남습니다. 같은 이전·새 프로젝트로 요청을 재시도하면 남은 삭제와 최종 전환을 다시 시도할 수 있습니다. 누락 Storage 파일(404)은 삭제된 것으로 처리됩니다.
- 다른 새 프로젝트로의 중복 변경 요청은 거절합니다.

**중요:** 이는 roll-forward(삭제 작업 재개)로, 이미 삭제된 파일을 복원하는 rollback이 아닙니다. 일반 사용자 슬롯 변경/기존 업로드 완료 경합 등은 여전히 실기기·Emulator 검증이 필요합니다. 승인·백업·실패 주입 테스트 전까지 PR Draft 및 운영 비활성 상태 유지.

## 프로젝트 백업 잠금과 쓰기 차단

- 교체 시작 시 관리자 슬롯의 `replacing` 상태와 `backupProjectLocks/{projectId}` 잠금 문서를 동일한 Firestore 트랜잭션에서 기록합니다.
- 일반/관리자 백업 예약 트랜잭션은 같은 잠금 문서를 읽어 교체 중이면 거부합니다.
- Firestore Rules는 프로젝트가 잠긴 동안 사진·영상 백업 메타데이터 생성/변경을 거부하고, 해당 프로젝트가 연결된 업로드 세션의 다른 프로젝트 ID 사용도 거부합니다.
- Storage Rules도 잠긴 프로젝트의 진행 중 업로드를 거부합니다. 앱/관리자 업로드 양쪽을 Firebase Rules Emulator에서 검사합니다.
- 서버는 잠금 기록 후 예약 세션을 재확인하고, 기존 파일/메타데이터 정리가 완료되어야 슬롯 변경과 잠금 해제를 동일 트랜잭션으로 처리합니다.
- 기존 업로드가 잠금과 경합하면 `replacing` 상태로 남을 수 있습니다. 해당 세션이 만료되거나 별도로 정리된 뒤 관리자가 같은 목표 프로젝트로 재시도해야 합니다.

**여전히 운영 전 검증 필요:** Cloud Storage 및 Firestore의 전체 파일 삭제는 원자적이지 않습니다. 잠금과 재시도는 신규 파일이 삭제 도중 생성되는 위험을 줄일 뿐, 손상되거나 삭제된 데이터를 복구하지 못합니다. 운영 관리자 삭제 스위치는 켜지지 않았으며 staging/실기기 점검 전까지 비활성으로 유지합니다.
