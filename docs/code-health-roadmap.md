# Body Frame 코드 건강도 및 레거시 정리 계획

## 원칙

출시 전 목표는 **기존 로컬 기록과 클라우드 데이터를 안전하게 유지하는 것**입니다. 보이는 파일 크기를 줄이기 위해 기능을 한번에 이전하거나 오래된 저장 키를 삭제하지 않습니다. Code-only 통과는 Android 실기기 동작을 보장하지 않습니다.

## 우선순위

1. **P0 기록 보존**: 사진 ID와 파일명 분리, 촬영/가져오기/정렬/삭제/이전 설치 마이그레이션 회귀 검사 및 기존 기록 실기기 QA
2. **P1 결제·백업·광고**: `main`과 미병합 PR의 정책을 통일하고 Google Play/AdMob/Firebase 실제 운영 구성과 테스트 결과 확인
3. **P2 사용자 경험**: 첫 사진/마지막 사진 비교, 화질·메모리·폴더블 조작 검증 후 점진적 개선
4. **P2 파일 분리**: 기존 동작 유지가 확인된 기능부터 작게 분리
5. **P3 레거시 정리**: 아래 경로의 실제 유입/데이터 호환성 확인 후 별도 PR로 제거

## 대형 파일의 제안된 분리 경계

| 경로 | 분리 후보 | 사전 검증 |
| --- | --- | --- |
| `features/camera/CameraScreen.tsx` | 네이티브 카메라 세션, 촬영 설정, 저장 큐, 가이드·포커스 | 저장 실패/다중 셔터/권한 거절/프로젝트 전환 |
| `features/records/BodyFrameProjectDetailScreen.tsx` | 사진 정렬, 앨범 가져오기, 수치 카드, 알림 설정 | 정렬·삭제·사진-수치 연결·스크롤 |
| `features/trip-clip/TripClipScreen.tsx` | 이전 영상 에디터 동선, 프레임 렌더링, 저장 로직 | 구버전 deep link 및 보관함 복원 |
| `lib/cloud-backup.ts` | 업로드 세션, 콘텐츠별 백업, 복원, 실패 큐 | 부분 실패·계정 전환·할당량·재시도 |
| `functions/index.js` | 결제, 일반 백업, 관리자 백업, 삭제·쿼터 핸들러 | Functions exports/권한/에뮬레이터 테스트 |

대형 파일은 하나의 PR에서 하나의 책임만 분리합니다. 외부 API와 저장 데이터 형식이 유지되는지 테스트한 뒤 다음 파일을 분리합니다.

## 기존 코드·식별자 정리 주의

- `app/legacy-studio.tsx`, `app/advanced-settings.tsx`, `features/studio/`, 기존 `TripClipScreen`은 현재 4개 기본 탭의 경로가 아니더라도 내부 이동이나 이전 앱 링크에서 사용할 수 있습니다. 호출 지점을 확인하지 않고 삭제하지 않습니다.
- `travel-frame.photos.v1`, `travel-frame.videos.v1`, `body-frame.projects.v1`, Firebase 사용자 문서 경로 및 기존 사진의 로컬 URI는 이미 설치된 앱의 데이터와 연결됩니다. 이름만 바꾸지 않습니다.
- 사용자에게 표시하는 문구부터 Body Frame으로 정리하되 저장소명, 패키지 ID(`com.haebi.photoguide`), 기존 Firebase 프로젝트 식별자는 독립적인 이전 계획 없이 변경하지 않습니다.

## 품질 기준

- PR은 변경 전후 데이터를 보존하는 실행형 테스트를 포함하고, 필요한 경우 신규 Android Development Build로 검증합니다.
- 테스트에서 `source.includes(...)`만 확인하는 구조 검사는 보조 수단이며, 실제 저장·복원·오류 복구는 가상 파일시스템 또는 에뮬레이터로 확인해야 합니다.
- PR 병합 전 GitHub Actions 상태 확인, 실제 기기 QA 체크리스트 갱신, 운영 변경이 필요한 작업의 별도 승인 절차를 지킵니다.
- 기존 로그인/구독/백업·삭제 흐름을 변경할 때 데이터 복구 계획을 먼저 작성합니다.
