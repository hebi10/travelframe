# Body Frame Stage 2 Design

## Goal
Implement the local project/folder foundation for Body Frame: project persistence, safe legacy-photo migration, project-scoped storage primitives, and the fixed Body Frame image-storage policy, without switching the current TravelFrame camera UI to the new project flow yet.

## Scope
- Add a local Body Frame project repository backed by AsyncStorage.
- Create a deterministic legacy project named `기존 사진` when pre-Body-Frame photos exist without `projectId`.
- Assign legacy photos to that project in chronological order with stable `sequence` values starting at 1.
- Migrate local photo and preview files into per-project directories while preserving remote/cloud-only entries without local file moves.
- Use physical paths shaped like `photos/<projectId>/001.jpg` and `photo-previews/<projectId>/001.jpg`.
- Add a dedicated Body Frame project-photo storage adapter for new project-aware saves.
- Keep the existing TravelFrame camera/photo-library save flow unchanged until Stage 3, where the camera will explicitly resolve the active project and call the new adapter.
- Extend photo save inputs with optional `projectId` / `sequence` so Stage 3 can connect without another domain-type change.
- Apply the fixed Body Frame app-image policy inside the new project-photo adapter: max long side 2560px, JPEG 0.85.
- Apply the fixed preview policy inside the new project-photo adapter: max long side 1080px, JPEG 0.74.
- Run a safe Stage 2 migration at app startup. Migration must be idempotent and must never delete a source file before new metadata has been persisted.

## Project Repository
Storage key: `body-frame.projects.v1`.

Required APIs:
- `getBodyProjects()`
- `getBodyProjectById(id)`
- `createBodyProject(input)`
- `updateBodyProject(id, patch)`
- `archiveBodyProject(id, archived)`
- `replaceBodyProjects(projects)` for migration/restore plumbing

Project IDs generated by the app must be filesystem-safe. The deterministic legacy project ID is `legacy-photos`.

## Legacy Migration Rules
- Only photos without a valid `projectId` are legacy candidates.
- Legacy candidates are sorted ascending by `createdAt`; ties are broken by `id` for deterministic ordering.
- They receive `sequence` values 1..N.
- The legacy project target count is `max(100, legacyPhotoCount)` so existing libraries larger than 100 do not immediately show an impossible target.
- The newest migrated photo becomes the project cover.
- Existing photos already assigned to another project are left unchanged.
- Existing storage key `travel-frame.photos.v1` is retained; migration writes the expanded metadata back through the existing photo-library persistence path.
- A migration completion marker is written only after migration succeeds.
- The migration still checks for newly unassigned photos on later launches, so compatibility saves made before Stage 3 can be migrated on the next startup.
- If migration fails before completion, the marker is not finalized and the next launch retries.

## File Migration Safety
For local files:
1. Create the project directory.
2. Copy the old file into a `.migrating` temporary destination in the project directory.
3. Move/replace that temporary file to the final `NNN.jpg` path.
4. Build the migrated photo metadata in memory.
5. Persist the project list.
6. Persist the complete photo list.
7. Only after both metadata writes succeed, delete obsolete old local source files.
8. Set the last-active project if no project was selected and then write the migration marker.

A crash before metadata persistence can leave harmless destination copies, but the old source remains. A retry safely overwrites the destination and completes metadata persistence before cleanup.

Remote URLs and `cloud_only` photo originals are not downloaded during migration; only project metadata is assigned. Local previews may still be moved when present.

## Project Photo Storage Adapter
`lib/body-frame-photo-storage.ts` owns the new Body Frame project file layout.

It provides:
- project photo URI generation
- project preview URI generation
- fixed-policy optimized local save
- fixed-policy preview generation
- migration of existing local files into project paths
- deferred cleanup of obsolete source files

Project paths:
- photo: `photos/<projectId>/<sequence>.jpg`
- preview: `photo-previews/<projectId>/<sequence>.jpg`
- sequence file names are zero-padded to at least three digits (`001.jpg`, `099.jpg`, `100.jpg`, `1000.jpg`).

Stage 2 deliberately does not route the existing camera save functions through this adapter yet. Stage 3 will select an active project, calculate the next sequence, and use this adapter from the new camera/project flow. This avoids changing the current production capture path before the project-selection UI exists.

## Image Optimization
Cloud-backup optimization keeps its existing user-selectable quality behavior.

The new Body Frame project-photo adapter uses a separate fixed local-storage policy:
- long side <= 2560px
- JPEG quality 0.85
- JPEG re-encoding removes unnecessary image metadata

Preview policy:
- long side <= 1080px
- JPEG quality 0.74

Existing photos are not batch re-encoded during migration; they are copied/moved as-is to avoid unnecessary quality loss and migration cost.

## Startup Wiring
`app/_layout.tsx` triggers `ensureBodyFrameStage2Migration()` once on startup. Failures are caught so the app can still start; migration state is retry-safe and a later startup can complete unfinished work.

The migration runs asynchronously alongside current app startup. Existing TravelFrame screens remain compatible with the old photo list while migration completes; Stage 3 will consume the project repository explicitly.

## Out of Scope
- Project switcher UI and project-management screens.
- Wiring the current camera to the project-photo storage adapter.
- Automatic reference-photo selection in the camera.
- Nth-record capture copy/UX.
- Progress-video rendering changes.
- Project-aware cloud backup of `BodyProject` documents.
- Google Play Billing.
- Branding and visual redesign.

## Verification
- A Stage 2 contract test runs immediately after the Stage 1 contract test and before the repository's known Android baseline failure.
- Pure migration helpers are tested for deterministic ordering, already-assigned-photo preservation, target count, cover selection, and path formatting.
- Source assertions verify project repository APIs, project storage adapter policy, temporary-copy behavior, metadata-before-cleanup migration ordering, and startup wiring.
- Typecheck and lint must pass.
- Existing repository-wide baseline failures are documented separately if still present.
