# Body Frame Stage 2 Design

## Goal
Implement the local project/folder foundation for Body Frame: project persistence, safe legacy-photo migration, project-aware photo paths, and the fixed Body Frame image-storage policy, without introducing the new camera/project UI yet.

## Scope
- Add a local Body Frame project repository backed by AsyncStorage.
- Create a deterministic legacy project named `기존 사진` when pre-Body-Frame photos exist without `projectId`.
- Assign legacy photos to that project in chronological order with stable `sequence` values starting at 1.
- Migrate local photo and preview files into per-project directories while preserving remote/cloud-only entries without local file moves.
- Use physical paths shaped like `photos/<projectId>/001.jpg` and `photo-previews/<projectId>/001.jpg`.
- Make new captured/edited photos project-aware when a project is provided or a last-active project is available.
- Preserve the existing unassigned-photo fallback when no project exists yet, so Stage 2 can remain compatible with the current UI before Stage 3 lands.
- Apply the fixed Body Frame app-image policy to new local photo saves: max long side 2560px, JPEG 0.85.
- Apply the fixed preview policy to newly generated previews: max long side 1080px, JPEG 0.74.
- Run a safe Stage 2 migration at app startup. Migration must be idempotent and must never delete a source file before new metadata has been persisted.

## Project Repository
Storage key: `body-frame.projects.v1`.

Required APIs:
- `getBodyProjects()`
- `getBodyProjectById(id)`
- `createBodyProject(input)`
- `updateBodyProject(id, patch)`
- `archiveBodyProject(id, archived)`
- `replaceBodyProjects(projects)` for migration/restore plumbing

Project IDs generated by the app must be filesystem-safe. The deterministic legacy project ID is `legacy-photos`.

## Legacy Migration Rules
- Only photos without a valid `projectId` are legacy candidates.
- Legacy candidates are sorted ascending by `createdAt`; ties are broken by `id` for deterministic ordering.
- They receive `sequence` values 1..N.
- The legacy project target count is `max(100, legacyPhotoCount)` so existing libraries larger than 100 do not immediately show an impossible target.
- The newest migrated photo becomes the project cover.
- Existing photos already assigned to another project are left unchanged.
- Existing storage key `travel-frame.photos.v1` is retained.
- A migration completion marker prevents duplicate work after a successful migration.
- If migration fails before metadata is persisted, the marker is not written and the next launch retries.

## File Migration Safety
For local files:
1. Create the project directory.
2. Copy the old file into a temporary destination in the project directory.
3. Move/replace the temporary destination to the final `NNN.jpg` path.
4. Build the migrated metadata in memory.
5. Persist the complete photo list and project list.
6. Only after persistence succeeds, delete obsolete old local files.

Remote URLs and `cloud_only` photos are not downloaded during migration; only project metadata is assigned.

## New Photo Storage
When a valid project is resolved:
- captured photo path: `photos/<projectId>/<sequence>.jpg`
- preview path: `photo-previews/<projectId>/<sequence>.jpg`
- sequence is explicit when supplied; otherwise it is the next available integer within that project.
- editing an existing project photo keeps its `projectId` and `sequence`.

When no project can be resolved, existing TravelFrame root-directory behavior remains as a compatibility fallback until Stage 3 creates/selects projects explicitly.

## Image Optimization
New app-local photo saves no longer use the user-selected backup quality as the storage policy.

Body Frame local-storage policy:
- long side <= 2560px
- JPEG quality 0.85
- JPEG output strips unnecessary metadata through re-encoding

Preview policy:
- long side <= 1080px
- JPEG quality 0.74

Existing photos are not batch re-encoded during migration; they are moved as-is to avoid unnecessary quality loss and migration cost.

## Startup Wiring
`app/_layout.tsx` triggers `ensureBodyFrameStage2Migration()` once on startup. Failures are caught so the app can still start; because the completion marker is not written on failure, migration is retried later.

## Out of Scope
- Project switcher UI and project-management screens.
- Automatic reference-photo selection in the camera.
- Nth-record capture copy/UX.
- Progress-video rendering changes.
- Project-aware cloud backup of `BodyProject` documents.
- Google Play Billing.
- Branding and visual redesign.

## Verification
- A Stage 2 contract test runs before the repository's known Android baseline failure.
- Pure migration helpers are tested for deterministic ordering, idempotent assignment, and path formatting.
- Source assertions verify safe migration ordering and startup wiring.
- Typecheck and lint must pass.
- Existing repository-wide baseline failures are documented separately if still present.
